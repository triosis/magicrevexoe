## Exact selection and authorization contract

Only an explicit private target JSON containing `hostingerWildcard` selects it.
It cannot coexist with `cloudStartup` or alternate allowedTriggerDefiners. Target
must pin production, HOSTINGER_LOCAL,127.0.0.1:3306, database
`u676472791_magicreview_db`, matched account
`u676472791_magicrev_user@127.0.0.1`, actual serverHostname, and no CA fields.
The exact account host must be independently verified; another matched account
refuses even if its username is similar. No production identity was queried here.

Required nested fields:

| Field | Required contract |
| --- | --- |
| phase |initial, verify, bootstrap or runtime; no automatic phase transition |
| approvalId |Genuine independently approved record; must match protected operator HOSTINGER_WILDCARD_APPROVAL_ID |
| operatorReference / recoveryReference / runtimeApprovalReference |Independently supplied review/rehearsal/steady-state records; references alone do not prove authorization |
| grantFingerprint |Fingerprint of precisely reviewed raw authority, not authentication hashes |
| manifestFingerprint |Canonical digest of unchanged actual schema manifest |
| releaseFingerprint |Actual installed compiled backend plus SQL/verification/manifest byte fingerprint |
| notBefore / expiresAt |UTC ISO datetimes; active positive window <=1hour for initial/verify/bootstrap, <=30days for runtime |
| riskAcknowledgement |Exact I_ACCEPT_WILDCARD_SCHEMA_AUTHORITY_AND_SHARED_DEFINER_RISK |

Record syntax uses existing8–80 ASCII letters/digits/dot/underscore/hyphen,
alphanumeric first, no REPLACE_WITH_ placeholder. No genuine production reference
is created by this tool. Signed record review/approver authority is an external
release gate; strings cannot establish that affected resources are owned by approver.

Transport approval remains independent: protected HOSTINGER_LOCAL_APPROVAL exact
acknowledgement and HOSTINGER_LOCAL_APPROVAL_ID matching target transport reference.
No API environment switch grants migration authority. Operator uses only protected
MIGRATION_DB_USER/PASSWORD, not DB_* fallback/dotenv. Bootstrap uses separate operator
BOOTSTRAP_* inputs, though the actual database principal is necessarily shared.

### Reviewed grant representation

Only one raw database-level row on the literal pattern text
`u676472791_magicreview_db` is accepted. The TO principal must match the exact
reviewed account. Optional global USAGE is allowed once; all other global grants,
roles/PUBLIC, table/other pattern rows, GRANT/ADMIN OPTION, unexpected resource
clauses, duplicate schema rows and changed patterns/privileges refuse. Auth clauses
may be present in SHOW GRANTS but are not logged or fingerprinted. Authority checks
also pin actual CURRENT_USER, no active role and MariaDB11.8.9.

Initial/verify/bootstrap require the reviewed ALL PRIVILEGES token. Runtime requires
exactly SELECT/INSERT/UPDATE/TRIGGER, no ALL/DELETE/CREATE/ALTER/DROP/other extras.
This policy does not purport to exhaustively prove a provider's hidden isolation
boundary. Unknown grant syntax fails closed for separate review, not normalization.

An independently reviewed fingerprint can be calculated offline with
`inspectWildcardGrants` using privately obtained full grant rows. Release identity
is calculated by `wildcardReleaseFingerprint()` from installed dist .js, migration
.sql and manifest bytes; it does not hash environment files, credential inputs or
node_modules. File paths/lengths and bytes are hashed in sorted order; symlinked
release entries refuse. Dependency/package/Node provenance remains a separate
artifact review requirement. Rebuilding/changing any pinned content needs fresh
release/policy/grant approval, not a bypass or automatic hash substitution.

## Final runtime viability and remaining blockers

**Engine-level reduced shared runtime is viable locally; actual Hostinger final
state remains unverified, therefore production NO-GO.** Do not assume hPanel has
the required TRIGGER control, removes ALL effectively, preserves exact raw pattern,
supports reviewed connections/metadata or keeps grants stable across updates.
No customer self-GRANT/REVOKE is proposed. Provider reduction must be independently
confirmed and performed only under later authorization, with closed/reconnected
application pools and actual denial tests. If it is unavailable, no permanent ALL
runtime mode exists here; do not initialize first and accept it afterward.

The wildcards still authorize matching existing/future schemas, potentially outside
known UI naming assumptions. Full ownership/boundary evidence and approver authority
are unresolved. Approval cannot turn this into exact isolation or consent for
another party's resources. Shared DML includes all tenant identities/roles/ledger;
TRIGGER permits replacing guards. Application RBAC does not constrain stolen-credential
SQL. HOSTINGER_LOCAL is unencrypted/no peer certificate; isolation is unknown.
External audit/recovery artifacts must not rely solely on the modifiable DB ledger.

Required before any future production work:

1. Owner/security accepts the changed wildcard/shared-definer contract and has
   authority for the full affected risk, or declines it and keeps NO-GO. Obtain
   independent transport, initial, bootstrap and enduring runtime approvals.
2. Establish actual full account/role/grant/version/target evidence and provider
   final reduction/persistence/new-session semantics. No invented references.
3. Accept tested provider/native production backup/isolated restore with original
   definers, keys, full data/schema and accountable recovery/RPO/RTO/custody.
4. Independently resolve exposed MFA candidate usage/remediation while preserving
   existing access key/ciphertext; private owner password and mandatory enrollment.
5. Review exact code/compiled artifact/dependencies and pinned release/manifest;
   authorize maintenance, migration, bootstrap, provider grant reduction, deployment
   and customer traffic separately. Keep API stopped while elevated.
